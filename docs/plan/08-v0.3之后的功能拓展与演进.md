## 4. v0.4 的最小完整范围

### 4.1 一条可体验的协作任务

保留河谷地图与现有物资。医生要在期限前完成送药，需要快递员把一份药材送到工坊；快递员接受工作单，自行选择仓库或药圃取材、运输并交给医生。医生实际收到药材后，自行制作、运输和交付药物。商人仍以固定规则参与竞争。

此版本包含 **两个独立规划角色＋一个固定背景角色**。工作单的创建/接受可采用确定的规则策略；各自的取材、路线、观察与任务恢复由规划器产生。医生等待到货时有唤醒条件和最晚结束时间。交接前不能把预计到货当作现有库存，也不能提前制作。

玩家可以阻路、移除材料、中断制作或按条款取消工作单。角色先通过合法观察或收到消息得知变化，再重新规划、发出状态通知、继续等待或明确失败。首版不承诺自主拆分任意团队任务。

| 优先级 | 功能 | 具体边界 |

| P0 | 资源仲裁与有界预留 | 只做本版交接和动作所需物资/工位；接受订单不自动锁住远端库存 |

本轮资源与消息设计要足以扩展，但不引入交易市场、任意动作 DSL、账号系统、分布式执行或大地图编辑器。

### 4.3 工作单协议

建议字段：`order_id`、`version`、`issuer`、`assignee`、`item`、`quantity`、`delivery_region`、`recipient`、`deadline_tick`、`revocation_policy`、`accepted_terms_hash`、`status`。字段含义和双方可见范围随协议发布。

状态为 `proposed → accepted → in_progress → fulfilled`；未接受可 `rejected/withdrawn`，接受后按条款 `cancelled`，超过期限 `expired`。`breached` 单独作为履约判定，不靠改写状态消除已经发生的违约。首版使用全额交付，不支持部分履约，避免分批数量语义混入第一切片。

关键规则：

1. 接受订单只建立义务，不产生物品。双方必须收到对应确认后才能在各自认知中使用承诺。
2. 订单条款变化有新版本；旧订单在改约正式生效前仍约束行动。目标修改不能隐式撤销已接受订单。
3. 物理转移、订单履约和对应回执作为同一权威提交处理。错误交付对象、数量或地点不能算履约。
4. 资源预留有期限，取消、失败和到期释放。强制玩家干预通过正规命令撤销受影响预留并结算动作。
5. 观察和消息描述角色能够知道的事实，不返回他人私有库存、计划或未通知的订单变化。
6. 履约可因世界变化失败，运行时记录原因与通知时刻；不能延长期限、无限重试或悄悄更换交付对象。

### 4.4 调度、等待与持久化

建议固定新协议的 tick 阶段：执行已排定的外生命令 → 完成到期动作并释放到期租约 → 投递消息与生成观察 → 基于已提交角色上下文作决策 → 仲裁新动作并提交 → 判定订单到期。外生中断先于动作完成，具体顺序随录制保存。

订单截止 tick 包含当 tick 已成功提交的交付：在 D tick 完成的交接可以履约，D tick 末仍未完成才到期。租约采用半开区间，动作预计完成 tick 必须小于租约截止值；失效租约不能用于完成动作。新生成的角色消息最早在下一 tick 投递，不形成同 tick 的无限对话/决策链。权威交付结果与收件方收到通知的时刻分别记录。

第一版采用 barrier，规划不消耗模拟时间。每个 NPC 只占一个前台动作，多个 NPC 可跨 tick 同时执行。失败竞争按有界等待年龄和确定轮换仲裁，不能永久优先固定 actor_id。一个角色用尽预算不应占住整个世界的推进权。Full/Local 对照采用相同的每角色额度与场景总额度，局部尝试、验证和回退全部计费，不能随角色增加给某一方法额外计算资源。

`waiting` 必须带原因、关注的可见事件、最晚唤醒/终止 tick。有效到货通知、目标变化或期限边界才触发决策；单纯每 tick 的相同状态不触发重复搜索。等待租约不允许持有半套资源。

显式存档新增全部角色状态、订单、预留、活动动作、消息队列、仲裁状态、预算和随机流。实际持久化只发生在一致的提交边界。仍可沿用活动会话在内存、显式存档持久化的产品边界；自动恢复活动服务器进程不是 v0.4 的前置条件。

## 5. v0.4 验收与失败标准

| 案例 | 必须观察到的结果 |
|---|---|
| 正常协作 | 下单、接受、取材、运输、交接、制作、最终交付均有实际状态变化 |
| 两角色争最后一份材料 | 只有一个获得资源；失败者收到可感知结果，不出现负库存或重复消费 |
| 隐藏断桥 | 未收到观察/报告的角色保持相同认知与决策；获知后才恢复 |
| 交付期限不足 | 原期限不变；规划提出等待、取消或明确失败，不能悄悄延时 |
| 取消、重复请求、重复回执 | 效果最多提交一次，资源结算一致；历史行为不回滚 |
| 制作/交接中途存档 | 恢复后不重复消耗或生产；待投递消息、期限和预算保持 |
| 延迟订单消息 | 权威状态与角色已知状态可暂时不同，界面明确展示，策略不偷读权威状态 |
| 循环等待/无材料 | 有界等待与 unknown/失败出口，停止后没有无效后台搜索 |
| 旧记录 | 0.1、0.2、0.2.1 的既有唯一轨迹及游标仍按旧协议验证，文件不改写 |
| 会话退出 | 活动任务、连接、消息和快照可释放；暂停/终态继续保持无无效轮询 |

记录最终任务成功率、订单按时履约率、无效提交数、预留泄漏、重复效果、总决策 CPU、节点/校验预算、等待时间和内存高水位。冻结用例中不允许存在已知的非法提交、重复消费或信息越界。

上线门槛以行为和不变量为准，不以测试总数增长为目标。复用状态机与协议参数化测试，保留每个新增故障模式的最小回归；旧证据目录继续只读，新实验写入独立工作目录。

## 6. v0.5：使协作成为可研究的恢复问题

### 6.1 证据与依赖

为事实保存多个支持来源，区分直接观察、收到的报告和预测结果。记录观察时间、接收时间、失效时间及支持对象。过期表示未知，冲突表示待查证；晚到的旧报告不能覆盖更新的直接证据。首版使用确定的优先规则，避免引入未经校准的概率置信度。

引入 `evidence_id → condition → action/order` 的反向索引，记录条件由观察支持还是由未来动作效果支持。工作单是预计供给与期限约束，实际交付才生成库存事实。一个计划可有线性执行顺序和旁挂依赖 DAG，无需直接实现通用部分序规划器。

收到合法的材料不足报告后，只定位受影响的取材、运输、制作、交付和订单节点；保留已执行事实，再检查替代片段的资源、时间及整个剩余计划。继续复用 0.2.1 已有的共享搜索队列思想；跨问题复用队列必须满足状态编码、目标与代价定义一致，不能机械复用过期状态。

### 6.2 主动获取信息与长动作

角色能比较「亲自检查、向已知角色询问、等待已接受交付、走已知替代路线」。排序可依据最近执行屏障、下游受影响步骤、信息获取时间与期限余量，先用确定启发式。Full 和 Local 使用相同观察规则与成本；另做消融才能归因主动观察收益。

加入维修者及 repair 长动作，使角色能在绕路与等待修桥之间选择。材料消耗、工位占用、开始/完成/中断效果各自明确，取消不抹去已投入资源。先覆盖有限动作目录，再判断是否有必要抽象通用 ActionSpec。

### 6.3 三个可证伪的假设

| 假设 | 比较方法 | 不成立时的处理 |
|---|---|---|
| 证据依赖索引降低无害变化和局部变化的恢复成本 | 同规划器 Full、粗粒度失效、精细依赖；其他观察/缓存/预算一致 | 保留解释价值，报告维护开销及适用范围 |
| 显式承诺依赖改善按期协作及计划稳定性 | 执行器同样检查订单；只消融规划器中的承诺预测/恢复机制 | 报告何时无增益，不把公共执行保障算作算法独有优势 |
| 任务相关的信息获取减少短 TTL 下无效循环 | 相同允许观察，对比现有探索规则与新选择器 | 报告额外搜索成本；无解困难案例继续保留 |

已有固定样例中缺材 Full/Local 为 66/66，隐藏断桥为 110/109，极短 TTL 无解场景仍昂贵。这说明下一步需要更有解释力的任务与指标，不能从这些数据推导 Local 已经普遍更优。

## 7. v0.6：场景复用与可信实验

将已被两个场景需要的配置提取为 `ScenarioSpec`：地图、动作目录版本、物资上限、角色能力、初始观察、目标、订单、外生干预和判定器。权威初始状态与角色公开配置分别加载，不能因配置化把隐藏库存送进规划上下文。

第二场景沿用原计划的「矿站供能」，至少改变资源依赖、期限结构和角色能力分布。例如两段线路检修共享一件工具，燃料运输与设备启动相互约束；不能只把药材改名为燃料。记录接入时修改了哪些模块；核心规划器若仍出现地点名特判，应先修复边界。

建立 Rules、GOAP、同规划器 Full/Local 与定义清楚的直接修复基线。论文启发的适配方法须标明差异，未经复现不得冠以原论文实验结果。原规划中的近期文献及创新边界在形成研究结论前重新核验全文。

主实验先采用离线 CPU/barrier。总决策 CPU 包含依赖维护、失效检测、观察决策、局部搜索、后缀验证和完整回退；动作执行、日志 I/O、网络和页面开销分报。当前界面 cpu_ms 的范围不足以直接承担这一指标。

冻结场景族、机制组合留出、可行性标签、预算、方法版本、主指标、失败分母与统计脚本。先用 8–12 个模板做试点，样本量再按配对方差与族内相关性确定。相同场景多次计时不算新增独立样本；不同策略走不同路线时允许合法获得不同观察。

沿用原计划的成功率非劣界 5 个百分点和成本改善 10% 作为**试点后待冻结的候选判据**，不是已达到目标。只有成功率差的单侧 95% 下界大于 −5 个百分点且成本比上界小于 0.90，才在注册任务分布上支持该收益结论。达不到时发布负结果或不确定结论，不放宽标准。

## 8. v0.7 与 1.0：接入真正的宿主

Godot 首个验证限定小型 2D 场景及 move/take/repair 三类动作，包含一次中断、重复命令和迟到回执。Godot 决定实际位置、物品和动作结果；Python 负责认知、规划及审计。只显示 Python 坐标的动画不足以证明外部执行能力。

协议明确 `command_id`、动作查询、结果确认、能力矩阵和恢复对账。Python 与 Godot 间没有天然跨进程事务，不能宣称任意外部效果 exactly-once。不支持快照的宿主只声明轨迹记录能力。

实时模式中世界持续推进，计算/网络延迟会影响到货与期限。用受控延迟桩先验证超时、乱序和过期响应，再单独考虑真实 API。barrier 与 realtime 的成功率、墙钟和 deadline miss 分开报告。

3/10/20 角色逐级标定空载、稳定动作、密集失效与恢复队列，记录 tick p95、决策等待、有效进展、截止失败和内存。规模取本机测量能够支持的范围，不能沿用原设计目标当实测承诺。

1.0 交付原规划六类成果：运行时 SDK、恢复算法、参考世界、调试工作台、评测套件、最小外部适配。补齐无需安装前端开发依赖的展示发行物、明确的协议兼容期、嵌入示例与复现入口。研究结论可以是“仅在部分结构下有效”，但接口、执行、回放与证据必须可靠。

## 9. 模型能力与展示交付的配套安排

模型接入下一步优先从一个真实供应商验证完整链路，而不是继续增加配置数量。建议顺序：离线目标语料与 Goal schema → 自然语言编译成受限目标 → 当前认知下的校验 → 少量受预算控制的真实调用 → 与无模型入口对照。

“送一些药去那边”之类无法确定数量/对象的输入应返回待澄清字段，不虚构隐藏实体。模型继续只提出候选，不修改世界；未使用过的目标组合与实际任务成功比长篇解释更有验证价值。自由对话、人格和长期记忆等可在核心运行时成熟后独立扩展。

真实 API 试验单独记录模型、时间、请求参数、用量和未知费用，既有额度、取消及不自动重试机制继续保留。需要实际凭据与明确调用预算时再落实运行配置；本规划不触发付费调用。

原首版计划的“公开可交互演示”仍未交付，可作为 v0.4 后的小型发布工作包：默认符号规划、清楚标注运行/录制模式、会话和 CPU 限额、可导入失败轨迹、五分钟操作导览。确定托管位置、持久磁盘及费用后再部署；不让托管工作阻塞核心协作研究，也不把本地启动称为已公开上线。

## 10. 控制架构与兼容成本

1. **从最新真实基线开始。** 核对并明确堆叠 PR 的交付基线，再创建功能分支；合并是独立的仓库操作，不能假定 main 已含 0.3。
2. **按需求拆模块。** 从现有 domain/planning_core/planner/engine 边界增加 actor、orders、resources 和 scenario 的实际实现；仅在多处复用时抽公共接口。
3. **保护旧执行语义。** v0.4 改变动作、状态和调度，必须新增录制协议。旧记录路由到冻结的动作/执行/规划组合，不能只冻结 planner 而修改共享 domain，导致旧哈希变化。
4. **控制内存与忙等。** 活跃订单、消息、证据支持集、规划队列和缓存有边界；终态对象能释放。持久历史与内存工作集分开，精确回放所需输入不能静默裁剪。
5. **保留公共执行保障。** Full/Local、模型与规则共用信息权限、动作检查和预算计费。研究消融不取消权威资源检查。
6. **增量保存可审核成果。** 实施时按 A–F 形成小提交并保存到远程开发分支，记录基线、验证及恢复步骤；新实现证据不覆盖历史报告。

建议正式启动时首先完成 A：冻结 v0.4 协作轨迹和协议，再做 B 的双角色状态切片。第一项可见成果应是“医生下单，快递员取材并交给医生”，随后用断桥与抢材把它推进到可恢复、可解释、可回放的协作任务。
